Версия: 1.0. Документ описывает **что** должно быть построено и **в каком

## 1. Результат (Definition of Done)

На сервере с **одной** видеокартой NVIDIA CMP 30HX (TU116, sm_75, 6 ГиБ)
развёрнут и работает веб-сервис, доступный по `http://<host>:8110/`, который:

1. Принимает микрофон из браузера, распознаёт речь **на лету** (стриминговый
   ASR), показывает промежуточную расшифровку в интерфейсе.
2. Каждый новый промежуточный результат распознавания **сразу же
   до-префилливается** в KV-кэш запущенной LLM, так что к моменту окончания
   фразы промпт уже посчитан и генерация стартует без паузы на prefill.
3. По окончании фразы (тишина) стримит ответ LLM токенами и **параллельно**
   отдаёт синтезированную речь — первый звук приходит до конца генерации текста.
4. Работает с TTS двух типов, переключаемых **из интерфейса**:
    - **qwen** — внешний сервис Qwen3-TTS, отдающий PCM потоком (по умолчанию);
    - **kokoro-ru** — Kokoro-82M ru внутри процесса голосового сервиса.
5. На той же карте поднимается **обычная Qwen3.5-0.8B** (`llama-server`,
   OpenAI-совместимый API на `127.0.0.1:8081`) — как задел для дальнейших
   разработок, с ключом доступа.
6. Агент умеет искать в интернете: подключён к MCP-серверу
   `https://ai.wormsoft.ru/api/mcp` инструментами `web_search` / `web_fetch`,
   токен берётся из `.env` (см. 6.1).
7. Все сервисы **прибиты к одной карте** (`CUDA_VISIBLE_DEVICES=0`), ни один
   процесс не растекается на другие устройства, потому что других нет.
8. Кроме голоса есть **текстовый режим ввода**: команду можно отправить
   текстом, а фактом окончания сообщения считается **нажатие Enter**, а не
   тишина. Ввод идёт в тот же конвейер (prefill → генерация → TTS) и является
   основным инструментом проверки инкрементального prefill без микрофона
   (см. 4.1 и 9.1).
9. Исполнитель **сам разворачивает сервис на сервере, поднимает юниты и сам
   тестово проверяет все ключевые кейсы через браузер** (см. 13.1), а не сдаёт
   «код, который должен работать». Результаты — в отчёте.
10. Есть README-отчёт: как собрано, какие замеры получены, какой контекст
    выбран и почему, как подключён MCP и где лежит токен, какие ограничения
    остались.

**Критерий «сделано»** — не «сервис отвечает», а таблица замеров из раздела 13
с выполненными порогами и воспроизводимыми командами проверки.

## 3. Архитектура

Четыре процесса, каждый — отдельный systemd-юнит, все на одной машине:

| Процесс | Что делает | Порт | Устройство |
|---|---|---|---|
| LLM-демон (свой, нативный) | держит `llama_context` Bonsai-9B, управляет KV вручную, отдаёт стриминг токенов | TCP `127.0.0.1:18521` | GPU0 |
| Voice-сервис (Python/ASGI) | ASR → prefill → генерация → TTS-очередь → WebSocket клиенту, плюс статика и HTTP | `127.0.0.1:8110` | CPU (ASR, оркестрация) |
| TTS-сервер qwen | Qwen3-TTS, PCM-стрим по HTTP | `127.0.0.1:8022` | GPU0 (в своём профиле) |
| LLM dev-сервер qwen08 | обычный `llama-server` с Qwen3.5-0.8B, OpenAI API + Bearer | `127.0.0.1:8081` | GPU0 (в своём профиле) |

Дополнительно: Kokoro-ru живёт **внутри** voice-сервиса (ONNX-сессия), отдельного
юнита не требует.

**Обязательно:** каждый процесс, трогающий GPU, стартует с пиннингом на карту
0. Без пиннинга демон раскидывает слои по всем видимым устройствам и вытесняет
   TTS — это уже случалось.

**Разрешение:** по умолчанию все порты слушают loopback. Наружу — только
voice-сервис, и только если это нужно для демонстрации.

## 4. Ядро №1 — инкрементальный prefill по партиалам ASR

Это главное требование. Обычный `llama-server` тут не подходит: он считает
промпт целиком на каждый запрос, и на CMP это секунды.

### Как должно быть устроено

1. Демон держит **один** `llama_context` и **один** последовательный слот
   (одна диалоговая сессия на процесс; многопользовательский режим не нужен).
2. Демон помнит токенизированный префикс, который уже лежит в KV
   (список токенов + их позиции). Это состояние — источник истины для
   «сколько уже посчитано».
3. На каждый новый текст приходит команда «префилл». Демон:
    - токенизирует полный промпт диалога (система + история + **реплика
      пользователя без хвоста ассистента**),
    - находит длину общего префикса с тем, что уже в KV,
    - если общий префикс короче — откатывает KV до этой точки,
    - декодирует **только новый хвост**,
    - возвращает статистику: сколько токенов взято из кэша, сколько досчитано,
      сколько всего в промпте, время в миллисекундах.
4. Ключевое свойство: промпт партиала **обрывается сразу после текста
   пользователя**. Пока ASR только удлиняет текст, каждый следующий промпт
   продолжает предыдущий токен-в-токен, и весь префикс берётся из кэша.
   Хвост ассистента (закрывающие токены реплики, маркер начала ответа,
   пустой think-блок) добавляется **только при генерации** — то есть его
   досчитывают один раз, в момент старта ответа.
5. Генерация — отдельная команда: строит полный промпт (с хвостом ассистента),
   добирает хвост и стримит токены клиенту построчно.
6. Откат KV: сначала пробуется частичный откат (`llama_memory_seq_rm`).
   Для гибридных моделей (linear+full attention) он для линейных слоёв
   возвращает «не могу» — тогда допустим **полный сброс с пересчётом**, но
   только как аварийный путь. Если сброс случается чаще, чем раз в несколько
   партиалов, — реализация неверна.
7. В клиенте голосового сервиса prefill вызывается по схеме «последний
   выигрывает»: пока считается один партиал, приходит следующий — предыдущий
   отменяется/перезаписывается, а не выстраивается в очередь. Иначе кэш
   отстаёт от речи.
8. Клиент **обязан** иметь таймаут на чтение ответа и переподключение при
   обрыве. Идемпотентные команды (префилл, статистика, сброс, установка
   инструментов) можно повторять один раз; генерацию — **нельзя** повторять
   никогда (частичный ответ уже ушёл в TTS).

### Требования к протоколу

Свой текстовый протокол поверх TCP: одна команда — одна строка, ответ —
одна JSON-строка или поток строк. Обязательный набор семантики:

| Команда | Смысл |
|---|---|
| проверка живости | ответ-пинг, используется health-чеком |
| префилл | текст реплики + необязательная история; ответ — статистика кэша |
| генерация | текст + лимит токенов + история; ответ — поток токенов и финальный блок со счётчиками |
| установка инструментов | список описаний функций в OpenAI-подобном формате; пустой список — выключить |
| сброс | забыть диалог, **база (системный промпт) остаётся в KV** |
| статистика | сколько токенов в KV, максимальная позиция, состояние инструментов |

Демон **многоклиентный** (неблокирующий опрос сокетов): диагностический
скрипт не должен вешать боевой сервис, а рестарт демона не должен навсегда
ломать voice-сервис (переподключение на следующей команде).

### Что считается браком

- Prefill считается всегда с нуля (`cached=0` на каждом партиале).
- Prefill считается после окончания фразы (то есть во время речи кэш пустой).
- Промпт партиала содержит хвост ассистента (тогда каждый партиал — полный
  пересчёт).

### 4.1. Текстовый ввод как основной стенд проверки prefill

Инкрементальный prefill невозможно принять, полагаясь только на микрофон:
живая речь невоспроизводима, а браузер с микрофоном есть не в каждой
консоли/туннеле. Поэтому **текстовый режим — обязательная часть**, а не
приятное дополнение.

Как должно работать:

1. В интерфейсе есть поле ввода текста. Пользователь (и агент) набирает фразу;
   сообщение уходит на сервер по Enter.
2. **Граница сообщения — нажатие Enter** (и только оно). Никакой тишины,
   никаких пауз, никакой автоотправки по простою: текст может набираться
   сколько угодно долго, отправка — явное действие.
3. Есть два режима, оба обязательны:
    - **простой Enter** — отправить всю набранную фразу целиком одним
      сообщением: сервер делает prefill + генерацию. Это основная проверка
      сквозного цикла без ASR.
    - **«Enter по словам»** (режим серии партиалов) — каждый Enter добавляет
      фрагмент к текущей фразе и сразу уходит в prefill, но **генерация НЕ
      стартует** (отдельная кнопка/второй Enter с пустым полем её запускает).
      Это главный инструмент проверки инкремента: серия «какой» → «сейчас» →
      «курс» → «биткоина» должна дать `cached` 0 → рост → рост, `new_tokens`
      по несколько штук, и только финальное действие запускает генерацию.
      Режим включается переключателем в интерфейсе; в обычной эксплуатации
      выключен, но в поставке **работает и проверен** — им будет
      пользоваться агент-исполнитель при приёмке.
4. Клиент и сервер для текстового ввода используют **тот же путь**, что и для
   ASR: события `промежуточный текст` / `финальный текст` → prefill по
   промежуточному → генерация по финальному. Никакой отдельной ветки
   «текстовый чат» со своим промптом и без кэша — иначе проверка бессмысленна.
5. После генерации и озвучки сеанс возвращается в готовность к вводу; история
   диалога, сборка KV и инструменты работают ровно так же, как в голосовом
   режиме.
6. Ограничения, которые надо соблюдать: пустой ввод не отправляется;
   ввод блокируется, пока идёт ход (или явно ставится в очередь); после
   отправки поле очищается; Shift+Enter — перенос строки, а не отправка.
7. Текстовый ввод должен быть доступен **всегда**, независимо от микрофона и
   от того, доступен ли браузерный аудиовход: это резервный и отладочный путь.

Обязательный вывод: каждое сообщение текстового ввода в панели KV даёт такую
же строку со статистикой `cached/new/ms`, как партиал ASR — без этого
проверка режима не считается выполненной.

## 5. Ядро №2 — базовый префикс снапшотом

Системный текст + описания инструментов — константа (ориентир: ~600 токенов
с пятью инструментами). На CMP её пересчёт на каждом ходу стоит 3–4 секунды.

Требование:

1. При старте демон один раз считает базовый промпт (система + блок
   инструментов) и сохраняет полное состояние последовательности через
   штатный механизм снапшота (`llama_state_seq_get_data`, размер буфера
   берётся из `llama_state_seq_get_size`).
2. Перед каждым ходом состояние восстанавливается
   (`llama_state_seq_set_data`), после чего декодится только хвост.
3. Это единственный способ «вернуться к базе» для гибридной модели:
   обычный откат KV не восстанавливает рекуррентное состояние линейных слоёв.
4. Команда «сброс» восстанавливает снапшот и **не трогает** базовую часть —
   после сброса кэш должен снова показывать `cached ≈ len(база)`.
5. Ожидаемый эффект (замер с рабочего стенда): `cached` был 0, стал 609;
   первый партиал 3792 мс → 17 мс; первый токен голосового цикла 16.9 с → 6.3 с.
6. При смене набора инструментов снапшот пересоздаётся (инвалидируется).

Альтернативный путь (снапшоты через `n_rs_seq` для частичного откатa)
**не использовать**: на 6 ГиБ это требует больше VRAM, чем есть, даже при
малом числе снапшотов. Если очень хочется — только с замером и только в
режиме малого контекста.

## 6. Ядро №3 — шаблон промпта, reasoning, инструменты

Формат — ChatML той модели, что используется (Qwen-семейство):

1. Реплики оборачиваются маркерами начала/конца сообщения; токенизация
   **обязана** идти с включённой обработкой спецтокенов, иначе разметка
   распадается на обычный текст и модель не видит границ реплик.
2. История рендерится **ровно так, как она лежит в KV**, включая think-блок у
   реплик ассистента. Иначе промпт расходится с кэшем сразу после маркера
   ответа, и каждый ход считается заново.
3. **Подавление reasoning:** в конец промпта добавляется пустой think-блок
   (открывающий маркер, переводы строк, закрывающий). Модель считает, что уже
   подумала, и сразу отвечает. Тонкость, проверенная дважды: открывающий
   маркер токенизируется как обычный текст, а закрывающий — как спецтокен;
   поэтому «просто переводы строк» вместо закрывающего маркера **не работает**,
   нужен именно литерал закрывающего маркера. Критерий приёмки: в ответе нет
   утечки рассуждений, число токенов на ответ — десятки, а не тысячи.
4. **Порядок в системном промпте критичен:** сначала системный текст (роль,
   стиль: коротко, по-русски, без markdown), затем блок описаний инструментов.
   Если перевернуть — модель игнорирует инструменты. Проверять матрицей
   вариантов при отладке.
5. **Tool calls:** модель вызывает функции разметкой в тексте ответа. Демон
   парсит её в структурированный список вызовов и **не отдаёт разметку в
   поток** (фильтр с удержанием хвоста, чтобы тег не утёк в TTS). Финальный
   блок ответа содержит признак «ответ завершён» / «есть вызовы» и список
   вызовов. Voice-сервис выполняет их, дописывает результаты в историю
   отдельной ролью и просит модель ответить ещё раз (ограничить число раундов,
   ориентир — 3).
6. Инструменты для реализации (минимальный набор): поиск в сети, загрузка
   страницы, текущее время, калькулятор, таймер. Секреты (токены) — только из
   переменной окружения или файла с правами 600; в логи и health-ответ
   попадает **только факт наличия и источник**, не значение.
7. Если инструменты не нужны — они отключаются одной переменной окружения,
   без правки кода.

### 6.1. Подключение к MCP-серверу `ai.wormsoft.ru/api/mcp` (поиск в интернете)

Это **обязательная** часть работы: агент должен уметь искать в интернете и
загружать страницы.

**Куда подключаться**

- Адрес по умолчанию: `https://ai.wormsoft.ru/api/mcp`, задаётся переменной
  (рекомендуемое имя `WORM_MCP_URL`) — чтобы при смене эндпоинта не
  пересобирать код.
- Транспорт: **HTTP POST, JSON-RPC 2.0**, один запрос — один JSON-ответ.
  Полноценные MCP-сессии (`initialize`, SSE, `Mcp-Session-Id`) для этой задачи
  не нужны: сервер принимает прямой вызов инструмента.
- Авторизация: заголовок `Authorization: Bearer <token>`.
- Метод вызова: `tools/call` с параметрами `{"name": ..., "arguments": {...}}`.
  Ответ читается как `result.content[]` (элементы с `type == "text"`),
  признак ошибки — `result.isError`, ошибка протокола — поле `error`.
- Нужны два инструмента сервера:
    - `web_search` — аргументы `{query, max_results}`, результат: выжимки
      (заголовок, фрагмент, ссылка);
    - `web_fetch` — аргументы `{url}`, результат: текст страницы (обрезать до
      разумного объёма, чтобы не съесть контекст модели).

**Откуда берётся токен (важно для приёмки)**

Токен пользователь кладёт **в файл `.env`** — так, как ему скажет исполнитель.
Отсюда требования:

1. Токен читается из переменной окружения (`.env`, `EnvironmentFile` юнита или
   сам процесс), приоритет — у переменной; файл-альтернатива (права 600, путь
   настраивается) поддерживается, но необязательна.
2. `.env` ищется по порядку: явный путь из переменной → `.env` в корне проекта →
   `.env` рядом с приложением. Уже заданные переменные **не перезаписываются**.
3. Чтение токена — **ленивое** (в момент первого вызова инструмента), а не на
   импорте модуля. Иначе результат зависит от порядка импортов и от того,
   успел ли загрузиться `.env`; и инструмент перестаёт работать при запуске из
   тестов/скриптов без основного приложения.
4. Если токена нет — инструмент не падает, а возвращает внятный текст ошибки
   с **перечнем проверенных путей** (`.env` в корне, `.env` рядом с
   приложением, файл токена). Модель получает этот текст как результат
   инструмента и может честно сказать «поиск недоступен», а не выдумывать
   ответ.
5. Токен **никогда** не попадает в логи, в поток клиенту, в ответ инструмента
   и в `/health`. В `/health` отдаётся только `{present: bool, source:
   "WORM_TOKEN" | путь к файлу | null}` — этого достаточно для диагностики.
6. Ошибки сети/HTTP (401, 5xx, таймаут) превращаются в короткий текст
   результата инструмента, без стектрейсов и без тела ответа, в котором может
   оказаться чувствительное.

**Поведение в диалоге**

- Модель сама решает, когда звать `web_search`; результаты возвращаются в
  историю отдельной ролью, после чего модель отвечает ещё раз (см. п. 5).
- Результаты поиска перед подачей в историю сжимаются: убрать дубли пробелов,
  обрезать по лимиту символов, оставить 3–5 фрагментов. Иначе промпт вырастает
  на тысячи токенов, а на CMP prefill дорогой.
- Текст результата должен быть пригоден для озвучки: без Markdown-таблиц и
  длинных URL внутри фразы.
- Таймаут на вызов MCP — не больше ~45 с, чтобы зависший поиск не блокировал
  разговор.
- Инструменты отключаются одной переменной окружения (для отладки без сети).

**Приёмка по этому пункту** — критерии № 10 и 10a в разделе 13.

## 7. ASR: стриминг «на лету»

Требования:

1. Стриминговый распознаватель (sherpa-onnx, модель T-one CTC, русский),
   работающий на CPU, поток PCM16 16 кГц моно.
2. Распознаватель создаётся **один раз** на сеанс и переиспользуется:
   на каждую фразу создаётся новый поток, сам распознаватель не пересоздаётся
   (пересоздание дорого).
3. Каждый поток «прогревается» лидирующей тишиной (~0.75 с) — иначе в начале
   фразы появляется фантомный токен.
4. Детекция конца фразы — те же правила, что на стенде: 2.4 с тишины,
   1.2 с тишины после непустого результата, 20 с максимальной длины фразы.
   Поведение «фраза закончилась» не изобретать заново.
5. При остановке записи хвост фразы добивается ~1 с тишины и принудительным
   завершением входа. Без этого модель теряет последние ~1 с речи — это
   свойство модели, а не баг.
6. ASR **обязан** выполняться не в event loop, а в отдельном рабочем потоке
   (один воркер на сеанс). Иначе он блокирует цикл событий и prefill не
   успевает идти во время речи.
7. Один и тот же набор событий (`промежуточный результат` / `финальный
   результат`) должен отдаваться независимо от того, где считается
   распознавание. Это позволяет позже вынести ASR в браузер (wasm) без
   изменения остального конвейера. В первой версии достаточно серверного
   режима, но интерфейс событий заложить сразу.
8. Аудио на сервер идёт по WebSocket бинарными сообщениями; текст партиала —
   отдельным JSON-сообщением клиенту.

## 8. TTS: два движка, поток и переключение

### 8.1 Общие требования

1. Единый внутренний интерфейс бэкенда: асинхронный поток байтов PCM16 mono,
   плюс атрибут «частота дискретизации», метод прогрева и метод «описание
   состояния» для health.
2. TTS **никогда не блокирует** чтение токенов LLM. Текст режется на клаузы
   по границам предложений (а для раннего старта — по запятой/тире), каждая
   клауза уходит в отдельную очередь, отдельный воркер синтезирует и шлёт
   аудио. Ориентиры нарезки: первая клауза от ~12 символов, ранний старт от
   ~60 символов, принудительная нарезка на 200–220 символах.
3. Прогрев моделей при старте сервиса (в фоне, не блокируя старт): без него
   первый ответ платит 1.5–3 с тишины.
4. Синтез пишется в 16-битный PCM; NaN/Inf санитизуется, иначе браузер
   получает мусор (известный баг fp16 на Turing).
5. Неизвестный голос — ошибка 400, выключенный TTS — 503, а не молчание.

### 8.2 qwen (по умолчанию)

- Внешний HTTP-сервис Qwen3-TTS (GGML-бэкенд с квантованными весами — путь,
  который на CMP даёт рабочие цифры: RTF 0.35–0.42 и первый звук ~0.4 с).
- Стриминг обязателен: сервер отдаёт PCM чанками по мере генерации, голосовой
  сервис **пересылает их клиенту сразу**, не накапливая ответ целиком.
- Настройки: адрес сервиса, спикер. Оба — через окружение.
- Известное ограничение, которое нужно зафиксировать в README: встроенные
  спикеры модели — не русские носители, акцент слышен. Клонирование голоса в
  объём этой задачи **не входит**.

### 8.3 kokoro-ru (альтернатива, переключается в интерфейсе)

- Kokoro-82M ru, ONNX в процессе голосового сервиса, голоса `sveta` /
  `masha` / `dima`.
- Варианты весов: fp32 (326 МБ), fp16, q8. **Брать fp32** — на стенде q8 на
  CPU оказался в 3 раза медленнее fp32, а fp16 портит аудио (высокий WER),
  он заявлен под WebGPU, не под CUDA.
- Провайдер: `cuda` предпочтительно (+675 МиБ VRAM, TTFB ~50 мс), `cpu` — как
  резерв. На проде CPU-режим дал RTF 1.25, то есть **медленнее реального
  времени**: озвучка будет захлёбываться. Если выбирается CPU — это нужно
  честно померить и указать в отчёте.
- Kokoro не авторегрессионный: «потокового» синтеза у него нет, поток
  эмулируется нарезкой на клаузы (см. 8.1). Это не считается нарушением
  требования «стримить»: первый звук должен приходить в пределах десятков
  миллисекунд после первой клаузы.
- Kokoro и Silero (torch) в одном процессе с GPU-ONNX **несовместимы**
  (конфликт CUDA-контекстов → segfault). Silero в этой задаче не нужен; если
  добавляется — только как единственный torch-бэкенд и только на CPU.

### 8.4 Переключение движка

- В интерфейсе — сегментированный переключатель «TTS: qwen | kokoro»
  (по аналогии с переключателем ASR), выбор запоминается в браузере.
- Клиент получает список доступных движков из конфиг-эндпоинта; недоступный
  движок показывается, но заблокирован, с подсказкой почему (нет модели, нет
  VRAM, сервер собран в режиме только одного движка).
- Сервер валидирует запрошенный движок на **каждом** запросе синтеза:
  неизвестный — 400, недоступный — 503.
- **Переключать движок во время разговора запрещено** (кнопки блокируются,
  пока идёт ход) — как и с ASR: посреди фразы подмена источника аудио даёт
  рассыпавшийся звук.
- Голос можно передавать параметром запроса; кэшировать бэкенды по имени
  голоса, чтобы не перезагружать модель.

## 9. Веб-интерфейс

Одна страница, отдаваемая сервисом:

1. Кнопка «Начать/Остановить разговор», индикатор состояния
   (слушаю / думаю / говорю).
2. Блок промежуточной расшифровки (то, что слышит ASR) и блок ответа
   (стримится токенами).
3. **Панель KV-кэша — обязательна.** Показывает по каждому партиалу: сколько
   токенов взято из кэша, сколько досчитано, всего в промпте, время prefill,
   отставание от речи, суммарные токены в KV. Это главный инструмент
   демонстрации того, что prefill инкрементальный. Без этой панели приёмка
   невозможна.
4. Журнал событий: вызовы инструментов и их результаты, метрики генерации
   (первый токен, ток/с, токены промпта/кэша/новые).
5. Переключатель TTS (раздел 8.4) и, опционально, переключатель ASR
   (сервер/браузер), если реализован клиентский ASR.
6. Захват микрофона: AudioWorklet (или эквивалент) → PCM16 16 кГц mono →
   WebSocket. Проигрывание аудио — по мере прихода чанков с корректной
   буферизацией по байтам (не по float32 — чанк может разрезать сэмпл).
7. Микрофон работает только в защищённом контексте (`localhost` или HTTPS).
   По IP без TLS браузер заблокирует доступ — предусмотреть в README инструкцию
   с SSH-туннелем и предупреждение в интерфейсе.
8. После проигрывания всей очереди аудио сервис возвращает сеанс в состояние
   «слушаю»; распознаватель при этом сбрасывается, но не пересоздаётся.
9. **Поле текстового ввода — обязательно** (см. 4.1): textarea/input +
   кнопка отправки; **Enter отправляет сообщение**, Shift+Enter — перенос
   строки. Рядом — переключатель «Enter по словам» (режим серии партиалов
   для проверки prefill) и подсказка, что именно сейчас произойдёт. Ввод
   доступен без микрофона и без TLS-контекста — это не связано с аудио.
10. Панель KV должна принимать статистику из **обоих** источников (ASR и
    текстовый ввод) и визуально различать их (метка источника в строке).
11. Рядом с полем ввода — быстрые кнопки готовых запросов для проверки
    (например: «Привет, как дела?», «Какой сейчас курс биткоина?»,
    «Который час?») — чтобы агент/тестировщик не набирал их вручную в браузере
    каждый раз.

## 10. VRAM-бюджет на одной карте: режимы и подбор контекста

**Это раздел, где нужно принимать решения по факту замеров.**

Доступно ~5749 МиБ. Арифметика (ориентиры, проверить):

| Компонент | МиБ |
|---|---|
| Bonsai-9B, веса | ~2355 |
| KV q8_0 при ctx 32K / 48K / 64K | ~544 / ~816 / ~1088 |
| compute-буферы LLM (+ запас) | ~200–300 |
| Qwen3-TTS 0.6B GGML Q8 | ~2300 |
| Qwen3-TTS 1.7B GGML Q8 | ~3437 |
| Qwen3.5-0.8B, ctx 32K | ~878 |
| Kokoro ru fp32 на CUDA | ~675 |

Вывод, который должен быть воспроизведён в отчёте: **все четыре тяжёлых
компонента одновременно в 6 ГиБ не помещаются.** Поэтому:

1. Обязательно реализуется **переключение режимов** (скрипт + описание):
    - **voice** (боевой, по умолчанию): LLM-демон 9B + TTS qwen (0.6B) +
      voice-сервис (ASR на CPU). Dev-сервис qwen08 и Kokoro-CUDA выключены.
    - **voice+kokoro**: LLM-демон 9B + voice-сервис с Kokoro на CUDA + ASR на
      CPU. TTS-сервер qwen выключен.
    - **dev**: LLM-демон 9B выключен (или сильно урезан), поднят qwen08 с
      ctx 32K + TTS-сервер. Для разработки и отладки инструментов.
    - **all-in** (только если замеры подтвердят): крайне малые контексты у всех
      сразу. Не обязателен, но если получится — задокументировать.
2. **Размер контекста подбирается экспериментально**, шагами (например
   16K → 24K → 32K → 48K → 64K) с записью в отчёт: `ctx`, фактические веса,
   KV, compute-буферы, свободная VRAM, работает ли decode. Максимум — там, где
   осталось ≥100 МиБ запаса и нет `cudaMalloc failed`.
3. **Минимально приемлемый контекст** для боевого режима — 16K; целевой —
   32–48K. Если для 9B с TTS 0.6B не удаётся получить даже 16K — разрешено
   понизить TTS до 0.6B в самом лёгком варианте или запускать TTS по
   требованию (старт по первому запросу, остановка по таймауту простоя), но это
   должно быть явно оформлено и замерено, а не «оно как-то работает».
4. Разрешённый и поощряемый приём: **деградация сервисов**. TTS-сервер и
   qwen08 могут быть `disabled`/`inactive` в systemd, а скрипт режима поднимает
   нужный набор. Health voice-сервиса обязан честно показывать, что TTS
   недоступен (503 на синтез, а не тишина).
5. Если ради VRAM приходится менять модель LLM — это **не** соответствует ТЗ.
   Bonsai-9B (PQ2_0) обязателен; 4B можно предложить как рекомендацию в отчёте,
   но боевой режим — 9B.
6. KV-кэш — q8_0 при включённом flash-attention. На sm_75 это требует сборки,
   где реализованы ядра quantized-KV flash-attention для Turing. Если ядро
   отсутствует (`has no device code compatible with CUDA arch 750`) —
   разрешён откат на KV f16 с **вдвое меньшим** контекстом, но факт отката
   фиксируется в отчёте как ограничение.
7. Модель обязана инициализироваться с `n_outputs_max = 1` и рабочим размером
   батча (ориентир — 256). Иначе llama.cpp резервирует logits-буфер на весь
   батч (сотни МиБ) и инициализация падает с OOM.

## 11. Конфигурация, юниты, секреты

1. **Всё через переменные окружения**, дефолты = значения целевой машины.
   Хардкод путей в коде запрещён: те же исходники должны запускаться на другой
   машине без правок.
2. Минимальный набор переменных (имена — рекомендация, смысл — требование):

| Группа | Что должно настраиваться |
|---|---|
| LLM-демон | путь к gguf, контекст, батч, потоки CPU, число слоёв на GPU, индекс GPU, порт, адрес bind, q8-KV вкл/выкл, прогрев вкл/выкл, режим снапшотов |
| Voice | адрес/порт LLM-демона, адрес/порт и спикер TTS, движок TTS, каталог модели Kokoro, вариант весов и провайдер, лимит токенов генерации, число раундов инструментов, включение инструментов, адрес/порт самого сервиса, каталог модели ASR, режим ASR |
| Инструменты | `WORM_MCP_URL` (дефолт `https://ai.wormsoft.ru/api/mcp`), токен значением (`WORM_TOKEN`), файл токена (`WORM_TOKEN_FILE`, дефолт `~/.wormsoft-token`), явный путь к env-файлу (`VOICE_ENV_FILE`), включение инструментов |

3. `.env` ищется в порядке: явный путь из переменной → `.env` в корне проекта →
   `.env` рядом с приложением. **Уже заданные переменные не перезаписываются**
   (приоритет у процесса/юнита). Парсер — свой, без внешних зависимостей;
   читать как UTF-8 с BOM, поддерживать `export KEY=value`, кавычки,
   комментарии. Отдельно защититься от CRLF: символ возврата каретки в
   значении (например, в токене) даёт невидимый хвост и ошибку 401.
4. Юниты systemd для всех четырёх процессов: `Restart=always`,
   `EnvironmentFile=-/etc/<name>.env`, `After/Wants` между LLM и voice,
   `User` — не root, никаких паролей в командной строке.
5. Секреты: файл с правами 600 либо переменная. В `/health` и логи — только
   `{есть/нет, источник}`. Тексты ошибок инструмента должны перечислять
   проверенные пути, но не содержимое.
6. Один и тот же код — для целевой машины и для локальной разработки; разница
   только в env.
7. В репозитории обязателен шаблон `.env.example` со всеми переменными, включая
   плейсхолдер токена MCP; сам `.env` в git не попадает (права 600). Исполнитель
   сообщает пользователю точный путь и имя переменной — туда он и кладёт токен.
8. Сетевой доступ: сервер должен уметь исходящий **HTTPS** к
   `ai.wormsoft.ru`. Если наружу только через proxy — предусмотреть переменные
   для него; если доступа нет вообще — это фиксируется как ограничение,
   поиск честно недоступен (критерий 10a).

## 13. Приёмочные критерии

Все пункты проверяются на целевой машине, с одной картой, и попадают в отчёт
с фактическими числами.

| № | Критерий | Порог |
|---|---|---|
| 1 | Демон инициализирует Bonsai-9B с KV q8_0 и FA | в логе нет ошибок CUDA, `decode` работает |
| 2 | База префикса в кэше | `cached_tokens` ≥ 500 (≈ системный промпт + инструменты) на первом же партиале хода |
| 3 | Инкремент на серии партиалов | на 5–7 партиалах: `new_tokens` ≤ 10, время prefill ≤ 100 мс (медиана), `cached` растёт |
| 4 | Первый токен после окончания речи | ≤ 2.5 с (ориентир 9B на CMP: 1.4–2.2 с) |
| 5 | Первый звук (qwen TTS) | ≤ 4.0 с от конца фразы (ориентир: 3.0 с) |
| 6 | Потоковость TTS | первый чанк приходит до окончания генерации текста; qwen — непрерывный PCM без разрывов дольше 300 мс |
| 7 | Kokoro-ru | синтезирует и звучит; TTFB ≤ 300 мс (CUDA) / ≤ 1.5 с (CPU); RTF измерен и указан |
| 8 | Переключение TTS из UI | работает без рестарта сервиса, заблокировано во время хода, выбор переживает перезагрузку страницы |
| 9 | ASR-стриминг | промежуточные результаты видны до конца фразы, финал приходит ≤ 500 мс после тишины |
| 10 | Инструменты + MCP wormsoft | на реальном запросе («какой сейчас курс биткоина») модель вызывает `web_search` через `ai.wormsoft.ru/api/mcp`, ответ содержит свежие данные, разметка вызова не утекает в TTS; токен есть в `.env`, `/health` показывает `present: true` и источник, само значение не светится нигде |
| 10a | Деградация без токена | если токен убрать: поиск отвечает «поиск недоступен» с перечнем проверенных путей, сервис продолжает работать, модель не выдумывает данные |
| 11 | Устойчивость | рестарт LLM-демона не требует рестарта voice-сервиса; `/health` возвращается в `ok` сам |
| 12 | VRAM | после прогрева свободно ≥ 100 МиБ; ни один процесс не использует второе устройство (устройства нет) |
| 13 | Один в один с эталоном | сценарий «вопрос → уточнение → ответ инструментом → второй ход» проходит end-to-end без ручных вмешательств |
| 14 | Текстовый ввод по Enter | Enter отправляет сообщение, Shift+Enter — перевод строки; текст проходит тот же путь prefill → генерация → TTS; в панели KV появляется строка со статистикой |
| 15 | Инкремент на тексте | серия из 4–6 «слов-партиалов» в режиме по Enter: `cached` растёт от партиала к партиалу, `new_tokens` ≤ 10 на каждом, генерация стартует только по финальному Enter |

Тестовые утилиты (свои, по образцу стенда): бенчмарк скорости LLM (первый
токен + ток/с + prefill), тест серии партиалов (печатает `cached/new` по
каждому), сквозной тест двух ходов через WebSocket, тест вызова инструмента,
распознавание контрольного wav-файла, замер TTFB/RTF для каждого TTS-движка,
тест текстового ввода по Enter (в том числе сценарий «слово за словом»).

## 13.1. Обязательный самостоятельный прогон в браузере

Сдача «код работает, у меня локально проверено» **не принимается**. Исполнитель
сам разворачивает сервис на целевой машине, поднимает юниты и сам проходит
сценарии ниже **в живом браузере**. Это отдельный этап работы, со своим
чекпойнтом в разделе 14 и своим разделом в отчёте.

**Как добраться до интерфейса:** микрофон работает только в защищённом
контексте. Значит — либо SSH-туннель на порт сервиса и `http://localhost:8110/`,
либо (если браузер и сервер на одной машине) прямой `localhost`. По IP без TLS
микрофон будет заблокирован — это надо предусмотреть в README и проверить
текстовый режим именно тем способом, который реально доступен.

**Матрица обязательных сценариев (каждый — скриншот в отчёт + цифры):**

| # | Что делать в браузере | Что должно получиться |
|---|---|---|
| B1 | Открыть страницу, дождаться статуса `ok` | интерфейс отрисован, нет ошибок в консоли (кроме допустимого favicon), `/health` = `ok` |
| B2 | Разрешить микрофон, сказать «привет, как дела», дождаться ответа | промежуточная расшифровка появляется во время речи, ответ звучит и печатается токенами |
| B3 | Набрать в поле ввода вопрос и нажать Enter | тот же цикл, что и голосом, но без микрофона; в панели KV — строка со статистикой |
| B4 | Включить режим «Enter по словам», отправить фразу в 4–6 приёмов | по каждому Enter видны `cached`/`new`/`ms`, `cached` растёт, генерация — только на финальном Enter |
| B5 | Переключить TTS на kokoro, повторить B3 | звучит другим голосом, ошибок нет, выбор сохраняется после F5 |
| B6 | Спросить «какой сейчас курс биткоина» | в журнале — вызов `web_search`, затем результат, затем ответ с реальными данными; разметка вызова не в TTS |
| B7 | Спросить второй раз в том же диалоге (например: «а эфира?») | история работает, кэш горячий (видно по `cached`), модель использует контекст |
| B8 | Во время разговора попробовать переключить TTS/ASR | кнопки заблокированы с подсказкой |
| B9 | Перезапустить LLM-демон на сервере, не трогая voice | UI показывает восстановление, следующий вопрос работает без перезагрузки страницы и без рестарта voice-сервиса |
| B10 | (Если доступен микрофон) проверить ограничения: длинная пауза >2.4 с делит фразу, после ответа сеанс возвращается в «слушаю» | нет рассыпавшегося текста, нет двойного старта генерации |

**Важно:** сценарии выполняет именно агент-исполнитель. Если браузер
недоступен из его окружения (нет графической сессии, нет туннеля) — это надо
**явно написать в отчёте** с указанием, что именно проверить не удалось и
как это проверить вручную, а не молча пропустить пункт.

## 14. Порядок работ (этапы и чекпойнты)

Этап нельзя считать закрытым, пока не снят замер и не записан в отчёт.

1. **База машины.** Проверить GPU (`nvidia-smi`), см_75, свободный диск,
   версию драйвера. Скачать модель Bonsai-9B PQ2_0 и модель ASR. Зафиксировать
   исходное состояние.
2. **Сборка llama.cpp под sm_75** (форк, поддерживающий тернарные веса) и
   проверка, что quantized-KV flash-attention для Turing работает. Если нет —
   зафиксировать и перейти на f16-KV с уменьшенным контекстом.
3. **LLM-демон.** Модель грузится, `ping` отвечает, `generate` стримит,
   reasoning подавлен (нет утечки), ответ осмысленный. Замер: первый токен,
   ток/с.
   3a. **MCP-поиск.** Отдельным скриптом: прямой `tools/call` `web_search` через
   `ai.wormsoft.ru/api/mcp` с токеном из `.env` возвращает непустые выдержки;
   затем то же через демон (модель сама вызывает инструмент). Чекпойнт:
   `/health` показывает `present: true`, поиск работает, значение нигде не
   залогировано.
4. **Инкрементальный prefill.** Серия партиалов: `cached` растёт, `new`
   маленький. Чекпойнт: критерии 2 и 3.
5. **Базовый префикс снапшотом.** `reset` не убивает базу. Чекпойнт: эффект
   «первый партиал десятки мс».
6. **Инструменты.** Установка описаний, парсинг вызовов, фильтр разметки,
   раунды. Чекпойнт: критерий 10.
7. **ASR-сервис.** Один recognizer на сеанс, прогрев, правила endpoint,
   добивка хвоста. Чекпойнт: критерий 9 на контрольном wav и в браузере.
8. **Voice-сервис и WebSocket.** Сквозной цикл с TTS=none (текстом).
   Чекпойнт: критерии 4, 11.
9. **TTS qwen.** Внешний сервис, стриминг, очередь, нарезка клауз, прогрев.
   Чекпойнт: критерии 5, 6.
10. **TTS kokoro-ru + переключатель.** Чекпойнты: критерии 7, 8.
11. **Подбор контекста и режимов.** Матрица замеров по ctx, фиксация профилей и
    скрипта переключения. Чекпойнт: критерии 12 и таблица VRAM в отчёте.
12. **Dev-сервис qwen08.** Поднят, ключ работает, описано, как включить и
    когда выключать.
13. **Интерфейс.** Панель KV, переключатели, журнал, текстовый ввод по Enter
    (оба режима), инструкция по микрофону.
14. **Развёртывание на сервере.** Юниты включены (`enable --now`), всё
    поднимается после рестарта машины, `/health` = `ok`, сервисы в режиме
    `voice` по умолчанию (раздел 10).
15. **Живой прогон в браузере.** Пройти все сценарии B1–B10 из 13.1 самому,
    со скриншотами и цифрами.
16. **Регресс.** Прогнать все тесты из разделов 13 и 13.1 подряд на финальной
    конфигурации, после холодного рестарта всех сервисов.

## 15. Грабли, которые уже собраны (не повторять)

1. **`parse_special` при токенизации.** Без него ChatML-разметка разваливается
   на текст, модель не видит границ реплик.
2. **`n_outputs_max`.** Не выставить 1 — logits-буфер на весь батч (сотни МиБ,
   при словаре ~250k) и OOM при инициализации контекста.
3. **Батч 256, не 512.** Иначе `failed to allocate compute pp buffers`.
   Длинный промпт (с инструментами) декодировать кусками по размеру батча.
4. **Гибридная память не откатывается частично.** `llama_memory_seq_rm` для
   linear-attention слоёв возвращает «не могу». Нужен фолбэк на полный сброс,
   и снапшоты для базы.
5. **Сгенерированные токены нужно дописывать в учёт KV.** Иначе позиции
   разъезжаются и следующий ход падает с `inconsistent sequence positions`.
   Маркер конца ответа тоже уходит в декод.
6. **История ассистента рендерится с think-блоком** — иначе промпт не совпадает
   с KV.
7. **Порядок системного промпта**: система до блока инструментов.
8. **Пиннинг на карту.** Без него демон размазывается по всем видимым GPU и
   вытесняет TTS.
9. **prefill без хвоста ассистента** — иначе инкремент не работает.
10. **Клиент демона без таймаута** вешает сервис навсегда, если демон занят.
11. **Рестарт демона** раньше навсегда ломал voice-сервис: нужен сброс сокета
    при обрыве и один повтор для идемпотентных команд.
    11a. **Токен из `.env` не подхватился.** Частые причины: файл лежит не там,
    где ищет сервис (каталог приложения, а не каталог проекта; в systemd —
    `EnvironmentFile`); CRLF после правки в Windows (`\r` в значении → 401);
    токен прочитан на импорте до загрузки `.env`. Диагностика — только через
    `/health` (наличие + источник), без печати значения.
    11b. **Инлайн-вызовы через ssh-обёртки** ломают JSON-RPC-тесты на кавычках.
    Проверять MCP отдельным скриптом-файлом.
    11c. **Текстовый ввод не должен быть отдельной веткой.** Соблазн сделать
    «просто чат» без KV — тогда проверка prefill бессмысленна. Текст
    обязан идти через те же события и тот же prefill.
    11d. **Автоотправка по таймауту в текстовом поле** портит весь замысел:
    граница сообщения — только Enter (в режиме «по словам» — каждый Enter).
    11e. **Микрофон по IP без TLS** — браузер молча блокирует доступ. В отчёте
    должно быть указано, каким именно способом проверялся звук.
12. **TTS внутри цикла генерации** блокирует чтение токенов (6 ток/с против 45).
    Только отдельная очередь и воркер.
13. **Ленивая загрузка TTS** = 1.5–3 с тишины на первом ответе. Нужен прогрев.
14. **Kokoro q8 на CPU медленнее fp32**, fp16 на CUDA портит аудио.
15. **onnxruntime-gpu и torch в одном процессе → segfault.** Бэкенды
    взаимоисключающие.
16. **`pkill -f <подстрока>`** убивает собственную сессию, если подстрока
    совпала с командной строкой. Только по PID.
17. **CRLF в `.env`** из Windows: `\r` остаётся в значении → 401 на токене.
18. **Многострочный heredoc с python-кодом** через ssh/агентские обёртки
    ломается на кавычках. Писать скрипт в файл и запускать файл.
19. **Модель 9B нестабильна в решении «звать ли инструмент»** для
    синтетических одиночных функций и для времени. Это свойство модели:
    проверять на реальном наборе из 5 инструментов, а не на одном.
20. **Панель KV — не украшение.** Без неё нельзя доказать, что prefill
    инкрементальный, и задача теряет смысл.

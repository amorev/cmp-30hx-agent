# CMP Voice Agent — голосовой LLM-агент на одной NVIDIA CMP 30HX (6 ГиБ)

Веб-сервис: микрофон → стриминговый ASR → **инкрементальный prefill** в KV →
стриминг ответа токенами → потоковый TTS. Плюс текстовый ввод, инструменты с
поиском в интернете через MCP и панель KV-кэша.

Всё живёт на **одной** карте (`CUDA_VISIBLE_DEVICES=0`): Bonsai-2 9B (PQ2_0) на
GPU, ASR T-one CTC и TTS (Silero v5_6 ru / Kokoro-ru fp32) на CPU.

> 🎬 **Видео, где обсуждается проект:**
> <https://t.me/gmoreva/1209>

> **Для агента-исполнителя: см. `AGENTS.md`** — там пошаговое развёртывание,
> грабли и правила диагностики. Этот README — пользовательская документация
> и обзор архитектуры.

```
cmp-30hx-agent/
├── daemon/        нативный LLM-демон (C++, llama.cpp API, ручной KV)
├── voice/         Python/ASGI: ASR, оркестрация, TTS, инструменты, UI
├── units/         шаблоны systemd (4 юнита)
├── scripts/       сборка, режимы VRAM, замеры
├── tests/         приёмочные тесты
└── .env.example   все переменные с дефолтами целевой машины
```

На сервере всё это развёрнуто в `~/cmp-voice/`.

| Процесс | Что делает | Порт | Устройство |
|---|---|---|---|
| `cmp-silero-tts.service` | Silero v5_6 ru (torch CPU-only), OpenAI-совместимый PCM-стрим | `127.0.0.1:8023` | **CPU** |
| `cmp-llm.service` — `daemon/bonsai_daemon` | держит `llama_context` Bonsai-9B, рулит KV, инкрементальный prefill, снапшот базы, стриминг токенов | TCP `127.0.0.1:18521` | GPU0 |
| `cmp-voice.service` — `voice/app.py` | ASR → prefill → генерация → TTS-очередь → WebSocket; статика и HTTP | `127.0.0.1:8110` | CPU (ASR, оркестрация), GPU по TTS-профилю |

процессе. Silero работает на CPU и VRAM не занимает.

## 3. Доступ к интерфейсу с микрофоном

Браузер разрешает микрофон **только в защищённом контексте**: `localhost` или
HTTPS. По IP без TLS микрофон молча блокируется — это не баг сервиса.

**SSH-туннель (рекомендуемый способ):**

```bash
ssh -N -L 8110:127.0.0.1:8110 ubuntu@<host>
# затем открыть http://localhost:8110/
```

> При запуске туннеля из скрипта/агента используйте полное отсоединение:
> `nohup ssh -f -N -L 8110:127.0.0.1:8110 host < /dev/null >/tmp/tun.log 2>&1 &`
> иначе процесс наследует пайп и «висит».

**Текстовый ввод работает всегда** — без микрофона и без TLS.

## 4. Текстовый ввод: два режима

Поле ввода находится в карточке «Текстовый ввод».

| Режим | Что делает |
|---|---|
| **простой Enter** (по умолчанию) | Enter отправляет всю фразу целиком: prefill + генерация. Shift+Enter — перенос строки. |
| **«Enter по словам»** (чекбокс) | Каждый Enter добавляет фрагмент и **сразу** уходит в prefill, генерация не стартует. Пустой Enter запускает генерацию. |

Оба режима идут **тем же путём**, что и ASR: события `partial`/`final` → prefill
→ генерация. Отдельной «чат-ветки» без KV нет — иначе проверка prefill
бессмысленна.

Каждое сообщение даёт строку в панели KV: `cached / new / ms / всего` с меткой
источника (`ASR` или `TEXT`).

## 5. Ядро: инкрементальный prefill

**Промпт партиала обрывается сразу после текста пользователя**:

```
<|im_start|>system
{системный текст}{блок инструментов}<|im_end|>
<|im_start|>user
{текст партиала}                     ← обрыв здесь
```

Пока ASR только удлиняет текст, каждый следующий промпт продолжает предыдущий
**токен-в-токен**, поэтому весь префикс берётся из KV и досчитывается только
хвост (несколько токенов).

Хвост ассистента добавляется **только при генерации**:

```
{промпт партиала}<|im_end|>
<|im_start|>assistant
<think>\n\n\n\n          ← пустой think-блок: подавление reasoning
```

Алгоритм (в `daemon/bonsai_daemon.cpp`):

1. токенизация полного промпта (`parse_special=true` — иначе ChatML рассыпается);
2. поиск длины общего префикса с тем, что уже в KV;
3. откат KV до этой точки (`llama_memory_seq_rm`); при отказе (гибридная
   модель, линейные слои) — аварийный путь: восстановление снапшота базы +
   пересчёт хвоста (счётчик `snapshot_fallbacks` в статистике);
4. декодирование **только нового хвоста** кусками по `BONSAI_BATCH`;
5. в ответ — `cached_tokens / new_tokens / prompt_tokens / ms`.

Клиент вызывает prefill по схеме **«последний выигрывает»**, но реализованной
как **слияние**, а не как отмена:

- один prefill в работе + не более одного отложенного (самый свежий);
- когда текущий завершается, сразу запускается отложенный;
- ничего не отменяется, поэтому прогресс кэша не теряется.

> Почему именно так. Наивная «отмена текущего при новом партиале» на клиенте
> НЕ останавливает демон: он досчитывает начатое, а новый запрос встаёт в
> очередь. При партиалах каждые 250–300 мс ни один prefill не успевает
> финишировать, и кэш не двигается вообще. Замер до правки: 11 партиалов →
> **1 строка KV**. После: 11 партиалов → **11 строк KV**, `cached` растёт
> 706→719 прямо во время речи.

Кроме того, `set_tools` (пересчёт снапшота базы, ~4 с) **стирает
накопленный KV**, поэтому он троттлится (не чаще раза в 15 с) и никогда не
выполняется во время речи или хода. Без этого `/health` каждые 4 секунды
сбрасывал кэш и обнулял всю работу партиалов.

### Базовый префикс снапшотом

Системный текст + описания инструментов — константа (~600 токенов). При старте
демон считает её один раз и сохраняет полное состояние последовательности
(`llama_state_seq_get_data`). Команда `reset` восстанавливает снапшот:
база остаётся в KV, история забывается. При смене набора инструментов снапшот
пересоздаётся.

## 6. Протокол демона

Одна команда — одна JSON-строка, ответ — JSON-строка или поток строк.
TCP, многоклиентный `poll` (диагностика не вешает боевой сервис).

| Команда | Смысл | Ответ |
|---|---|---|
| `{"cmd":"ping"}` | живость | `{"ok":true,"pong":true}` |
| `{"cmd":"prefill","text":...,"history":[...]}` | до-префилл партиала | `cached_tokens,new_tokens,prompt_tokens,ms,ms_f,kv_tokens,fallbacks` |
| `{"cmd":"generate","text":...,"max_tokens":N,"history":[...]}` | генерация | поток `{"type":"token","text":...}`, затем `{"type":"done",...}` |
| `{"cmd":"set_tools","tools":[...]}` | описания функций (OpenAI-формат); `[]` — выключить | `tools,base_tokens,snapshot_kib` |
| `{"cmd":"reset"}` | забыть диалог, база остаётся | `cached_tokens` |
| `{"cmd":"stat"}` | статистика | `kv_tokens,base_tokens,pos_max,ctx,kv_type,tools,...` |

`generate` **никогда не повторяется** клиентом: часть ответа уже ушла в TTS.
Идемпотентные команды повторяются один раз при обрыве.

## 7. ChatML и инструменты

- Токенизация с `parse_special` — обязательно.
- История ассистента рендерится **с think-блоком**, ровно как лежит в KV, иначе
  промпт расходится с кэшем и каждый ход считается заново.
- Порядок в системном промпте: **сначала системный текст, потом блок
  инструментов** (если перевернуть — модель игнорирует инструменты).
- Вызовы разбираются из разметки `<tool_call><function=...>` и **не утекают в
  поток**: фильтр удерживает хвост, который может оказаться началом тега.
- **В историю пишется сырой текст генерации (`done.raw`) вместе с разметкой
  вызова.** Если положить туда только очищенный ответ, модель не знает, что
  сама вызвала функцию, и на результате поиска отвечает «откуда вы хотели
  узнать?» или выдумывает факты.
- Результаты инструментов дописываются ролью `user` с обёрткой
  `<tool_response>`, затем модель отвечает ещё раз (лимит раундов —
  `VOICE_MAX_TOOL_ROUNDS`, по умолчанию 3). Продолжение идёт командой
  `generate` с флагом `continue: true`: промпт уже заканчивается блоком
  результатов, и **пустая реплика пользователя не добавляется**.
- Результат подаётся как явные «готовые данные для ответа» с повтором
  исходного запроса. Объём сжатия — до 4 фрагментов / 900 символов:
  на длинных выдачах 9B сбивается с вопроса.

> **Ограничение модели.** Qwen3.5-Bonsai-9B не всегда сама решает вызвать
> функцию для «неявных» вопросов: «кто владелец FromSoftware» — не вызовет,
> а «найди в интернете кто владелец FromSoftware» — вызовет. Это свойство
> модели (грабли №19 в ТЗ), а не дефект сервиса: сам вызов, получение
> результата, второй раунд и озвучка работают. Формулируйте запрос явно.

Набор инструментов: `web_search`, `web_fetch`, `current_time`, `calculator`,
`set_timer`, `check_timer`. Отключаются одной переменной:
`VOICE_TOOLS_ENABLED=0`.

## 8. MCP-поиск: куда класть токен

**Точный путь:** `/home/ubuntu/.wormsoft-token`, **права `600`**, одна строка —
сам токен, без кавычек и `export`.

```bash
printf '%s' '<ТОКЕН>' > ~/.wormsoft-token
chmod 600 ~/.wormsoft-token
```

Альтернативы (приоритет — у переменной окружения):

| Способ | Имя / путь |
|---|---|
| переменная | `WORM_TOKEN` |
| файл токена | `WORM_TOKEN_FILE` (по умолчанию `~/.wormsoft-token`) |
| env-файл | `VOICE_ENV_FILE` → иначе `.env` в корне проекта → иначе `.env` рядом с приложением |

Эндпоинт: `WORM_MCP_URL` (по умолчанию `https://ai.wormsoft.ru/api/mcp`).
Транспорт — прямой JSON-RPC `tools/call`, заголовок `Authorization: Bearer <token>`.

**Правила:**
- токен читается **лениво** (при первом вызове инструмента), не на импорте;
- в `/health` — только `{"present": bool, "source": "WORM_TOKEN" | путь | null}`;
- значение не попадает в логи, поток клиенту и ответы инструментов;
- нет токена → инструмент возвращает текст с **перечнем проверенных путей**,
  сервис продолжает работать, модель честно говорит «поиск недоступен»;
- ошибки сети/HTTP → короткий текст, без стектрейсов и тела ответа;
- `.env` парсится своим кодом: UTF-8 с BOM, `export`, кавычки, комментарии,
  **CRLF вычищается** (иначе `\r` в токене даёт 401).

## 9. TTS: два движка

Переключатель в интерфейсе (`TTS: silero | kokoro`), выбор запоминается в
браузере. Во время хода переключатели заблокированы. Неизвестный движок —
`400`, недоступный — `503`.

| Движок | Где | Стриминг | Замечания |
|---|---|---|---|
| **silero** (по умолчанию) | отдельный процесс `cmp-silero-tts` (torch CPU-only), порт 8023 | эмуляция нарезкой на клаузы | Silero **v5_6 ru**, диктор **`xenia`** (есть также `aidar`, `baya`, `kseniya`, `eugene`), 48 кГц |
| **kokoro-ru** | ONNX в процессе voice-сервиса | эмуляция нарезкой на клаузы | голоса `sveta`/`masha`/`dima`, веса **fp32** (q8 на CPU втрое медленнее, fp16 портит аудио) |

### Нормализация текста для Silero

У моделей Silero нет цифр в токенсете, а из латиницы поддержаны единичные
буквы (опубликованный токенсет `v4_cyrillic`: `!,-.:?iµö` + кириллица).
Без предобработки «в 2024 году» читается как «в году», а «Python» просто
выпадает.

Поэтому текст проходит нормализацию **до** синтеза (`silero/normalize.py`,
вызывается в `silero/app.py`):

| Что | Было | Стало |
|---|---|---|
| числа | `15` | `пятнадцать` |
| годы + падеж | `в 2024 году` | `в две тысячи двадцать четвёртом году` |
| диапазон годов | `с 2020 по 2024` | `с две тысячи двадцатого по две тысячи двадцать четвёртый год` |
| дата | `12.05.2024` | `двенадцатое мая две тысячи двадцать четвёртого года` |
| время | `14:30` | `четырнадцать часов тридцать минут` |
| проценты | `15%` | `пятнадцать процентов` |
| деньги | `1 000 ₽` | `тысяча рублей` |
| дроби | `3,5` | `три целых пять десятых` |
| единицы | `2,5 кг` | `две целых пять десятых килограмма` |
| сокращения | `5 шт.` | `пять штук` |
| телефоны | `8-800-555-35-35` | `восемь, восемьсот, ...` |
| латиница | `Python`, `API` | `Питон`, `а-пи-ай` (словарь + транслит) |

Согласование — эвристика по окончанию следующего слова, а не морфология:
после 2–4 родительный падеж единственного числа на `-а/-я` даёт мужской род
(`два стола`), множественное на `-и/-ы` — женский (`две книги`). Отключается:
`SILERO_NORMALIZE=0` (полностью) и `SILERO_NORMALIZE_LATIN=0` (только
транслит). Флаг виден в `/health` как `normalize`.

Нарезка на клаузы в `voice/tts.py` не разрывает числа: граница «3,» + «5 кг»
сдвигается до конца числа, иначе дробь прочиталась бы как два числа.

Замерено на целевой машине:

| Движок | TTFB | RTF | Устройство |
|---|---|---|---|
| **silero v5_6 (xenia)** | **88–239 мс** | **0.07–0.08** | CPU |
| kokoro-ru fp32 | 382–525 мс | 0.12–0.28 | CUDA |
| kokoro-ru fp32 | 1129–4848 мс | 0.60 | CPU |

Silero выбран по умолчанию: лучший RTF из доступных и **ноль VRAM** — вся
память карты отдана модели LLM. Kokoro на CUDA возможен, но требует свободных
~700 МиБ и потому переключается отдельным профилем (`scripts/mode.sh
voice+kokoro`).

> Qwen3-TTS (GGML, `qwentts.cpp`) **выведен из поставки**: его 2.3 ГиБ VRAM
> нужны модели LLM.

Нарезка на клаузы: первая от ~12 символов, ранний старт от ~60 (по запятой),
принудительная нарезка на 210. TTS **никогда не блокирует** чтение токенов:
отдельная очередь + воркер на сеанс.

> **Torch и onnxruntime-gpu в одном процессе несовместимы** (конфликт
> CUDA-контекстов → segfault). Kokoro-ONNX — единственный GPU-бэкенд в
> voice-сервисе.

## 10. VRAM-бюджет и режимы

Доступно ~5749 МиБ. Все четыре тяжёлых компонента одновременно не помещаются —
профили переключает `scripts/mode.sh`:

| Режим | Состав | Когда |
|---|---|---|
| **voice** (по умолчанию) | LLM-демон 9B (ctx 24576) + Silero (CPU) + Kokoro (CPU) | боевой, **2751 МиБ**, запас 3393 МиБ |

## 14. Известные ограничения

- **Одна карта.** Все процессы стартуют с `CUDA_VISIBLE_DEVICES=0`; при
  отсутствии пиннинга демон раскидывает слои по всем видимым устройствам.
- **Контекст подбирается замерами** (см. отчёт): на CMP prefill и decode упираются
  в память, длинный контекст дорог.
- **Kokoro на CPU** может давать RTF > 1 (медленнее реального времени): озвучка
  будет захлёбываться. Рабочий вариант — CUDA-провайдер (профиль
  `voice+kokoro`), но он забирает ~700 МиБ VRAM у модели.
- **Silero нельзя запускать внутри voice-сервиса**: torch и onnxruntime-gpu
  конфликтуют по CUDA-контекстам (segfault). Поэтому это отдельный процесс
  с `CUDA_VISIBLE_DEVICES=""` — модель считает строго на CPU, но за счёт
  этого даёт лучший RTF из трёх (0.07) и не занимает VRAM вообще.
- **Qwen3-TTS**: встроенные спикеры не русские носители, акцент слышен.
- **Микрофон по IP без TLS** браузер блокирует — только туннель/localhost.
- Клиентский (wasm) ASR не реализован: заложен только интерфейс событий.
- Нет HTTPS и аутентификации интерфейса — доступ через туннель/VPN.
